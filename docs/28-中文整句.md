# 28 · 中文整句（`--lang zh`）

> 状态：**P1 已落地**（2026-11-01）。英文路径逐字节不变，中文路径是独立模块。
> 人读抽检的 10 条对照表在 §8，**结论待 Lead 复核签收**（机器判据 ≠ 母语审校通过，见 §9）。
> 本文不写本机路径；命令都在仓库根目录执行。

---

## 1. 一句话

`--lang zh` **不是词表替换**。词表替换只会把 `yellow raincoat` 换成「黄色雨衣」，
骨架还是英文的 `subject, with X, wearing Y, in the Z`，于是得到
「一个28岁的女人，带着黑色长发，穿着白色高领毛衣，在左前景」——中文不这么说话。

本次做的是三件事：

1. **整句重排**：主体+动作先落住，再场景、镜头、光、材质/媒介、画面文字；方位由
   动词/介词引出（「坐在画面左前景」），不是像英文那样裸挂在句尾；
2. **中文语法落点**：量词（一个人 / 一杯柠檬水 / 一盏台灯）、「的」字结构、
   定语与谓语分工（「穿着白色高领毛衣（面料柔软、合身）」）、全角标点；
3. **机检判据**：`zh_issues()` 用 7 条规则把「英文语序」变成可单测的东西，
   不靠人眼（§5）。

实现位置：`moss_llm/smith/zh.py`（新模块，整条中文路径不碰英文路径的代码）。

---

## 2. 为什么不直接在 `clauses.py` 里加分支

英文路径的价值是「默认输出逐字节不变」，而它被 **4 份真机 IR × 5 个后端**的 sha256
基线钉着（`tools/freeze_smith_set.py --check`）。往 `build_clauses()` / `render_prose()`
里插 `if lang == "zh"` 的改法，会让英文路径多一次被顺手改坏的机会。

所以中文路径**整条独立**：自己的子句计划（`build_clauses_zh`）、自己的句子拼装
（`render_prose_zh` / `render_tags_zh`）、自己的判据（`zh_issues`）。
`clauses.py` 只被当数据结构复用（`Clause` / `pack` / `DIM_ORDER`），**一行没改**。

代价是子句编排逻辑有两份。取舍：英文路径的「逐字节不变」是硬验收，而中文的维度顺序
本来就要按方言重排；共用编排反而会为了「两边都能用」把英文路径改成参数化。
`tests/test_lang_zh.py` 里有一条单测直接对 freeze 基线的 sha256 对账（§7），
两份实现谁被改坏都会红。

## 3. 入口与开关语义

| 入口 | 写法 | 行为 |
|---|---|---|
| CLI `compile` / `lint` | `--lang zh` / `--lang en` | 显式指定；不填走 registry |
| 门面 API | `compile_ir(ir, target, ..., lang="zh")` | 可选参数，默认 `None`；节点接口不改 |
| registry | `target.prompt.language` | **只读复用**：`zh` / `zh+en` → 中文路径；`en` → 英文（结构没动） |

优先级：**显式 `lang` > registry**。所以：

- 所有现存 target 的 `prompt.language` 都是 `en` ⇒ 默认行为与改前一致；
- 想临时出中文：`--lang zh`，不用改 registry；
- 自己接的 target 若把 `prompt.language` 写成 `zh`，则默认就出中文。

### 3.1 哪些情况**不走**中文整句（有意，不是漏做）

| 情况 | 行为 | 理由 |
|---|---|---|
| `moss-image` 有 bbox → Layout JSON | 原样输出 + warning | JSON 方言里坐标是事实，句子不是载体；硬翻会丢坐标对账 |
| `flux3` 有 bbox → caption + bbox 表 | 原样输出 + warning | bbox 表的 `desc`/`text` 字段是结构化的，不是一句话 |
| `task` = edit / inpaint / outpaint | 原样输出 + warning | 编辑指令是用户意图原文（逐字），翻译=改意图 |
| `minimax-h3`（timeline） | 原样输出 + warning | H3 自带中文骨架（`language: zh+en`），是另一套格式，不能当图像后端 zh 用 |
| `--lang zh` + `--mode llm` | **明确报错退出** | 扩写提示词是英文驱动，中文整句没有对应的扩写实现；宁可拒绝也不静默降级 |

`compile_ir(lang="zh")` 在以上情况下不会返回 `lang: zh` 键（没真翻就不冒充翻了），
warning 会说明原因。

## 4. 语序模板

### 4.1 维度顺序

默认（MOSS / Qwen / FLUX 3 / SDXL）：

```
主体+动作 → 场景 → 镜头 → 光 → 材质/媒介 → 画面文字
```

结构化的维度顺序沿用 `adapter.dim_order`——**方言参数化**，不是全局真理：

- **Krea 2**：`medium` 打头（官方要求媒介词开头）→ `摄影作品。柔和的电影感光线……一个28岁的女人……`
- **SDXL**：tag 方言 + `BREAK` 分块，每块 ≤75 token（中文按字计 ∝ 1 token），切块不砍句
- 观察散文（`notes`）按它所属的维度归位，且**单独成句**（不参与逗号并列，避免句中冒主语）

同一维度里多个主体用「；」分句（中文并列主语），其余维度用「，」并列。

### 4.2 句内模板

**人物**（主体 + 动作 + 方位先落住）：

```
一个{年龄}岁的{性别名词} + {动作}{在/位于}{方位} ，{头发}，{肤色}，{脸型}，{神情}，
穿着{衣物}（{面料/版型}），手里拿着{持物}，旁边放着{陈设}
```

例：

> 一个28岁的女人**坐在画面左前景**，黑色长发，扎在脑后，皮肤白皙、光滑，脸型椭圆，
> 表情中性，若有所思，略带忧郁，穿着白色高领毛衣（面料柔软、合身），手里拿着一杯柠檬水。

**关系句**（短指代，不复述外观；长方位短语只留名词，避免「的」字堆叠）：

> 画面左前景的女人**面向**画面右前景的男人
> 女孩**在**男孩**的左边**

**图内文字**（逐字，单独成句；中文内容用「」，拉丁内容用 `""` 便于 lint 的引号保护）：

> 画面上的文字是「写不下去」，字号偏小，常规字重，黑色字，居中排列，无衬线字体，
> 位置在右上方画格中央偏右。

**镜头**：`中景，平视，50mm 镜头，浅景深，对焦在桌边的两个人。`
**光**：`柔和暖光从正面和侧面照来，环境光补光，黄昏时分，氛围亲密而沉静。`
**场景**：`雨后京都一条狭窄的后街，湿漉漉的沥青路面倒映着店铺招牌，构图采用三分法，右上方留白。`
**媒介**：`摄影作品，35mm 胶片。`

### 4.3 量词与「的」字约定

- 人物统一 `一个N岁的{女人|男人|女孩|男孩}`；持物按名词配量词：一杯 / 一盏 / 一把 / 一支 / 一本；
- `的` 只出现在**修饰关系**里；方位短语长到需要两层「的」时，关系句退化成名词
  （「女孩在男孩的左边」），不写「画面左侧三分之一处的中景的女孩在……」；
- 句首不用「的/地/得/了/着/是」起手（半截句特征，机检 Z05）。

## 5. 机检规则：把「英文语序」变成可单测的东西

`zh_issues(text, ir=None, dim_order=None) -> list[str]`，空列表 = 通过。
会先把**允许保留英文的部分**挖空再判：引号内的逐字文字、IR 里的图内文字/画师署名/
`must_keep`、技术单位（`50mm`）、`BREAK` 分隔符。

| 码 | 判据 | 为什么算「英文语序」 |
|---|---|---|
| **Z01** | 引号外出现英文功能词 `a/an/the/of/with/in/on/at/and/…` | 中文句子不靠功能词连接；出现即说明骨架没换 |
| **Z02** | 引号外出现未翻译拉丁词 | 词表外残留要**点名**，不能静默吞掉或假装翻过 |
| **Z03** | 引号外混入 ASCII 标点 `, . : ; ( ) [ ]` | 英文逗号/句号链是英文句子切分方式；中文用全角 |
| **Z04** | 「的」字堆叠（`的X的`，X ≤1 字） | `of the … of the` 的直译痕迹 |
| **Z05** | 句首虚词（的/地/得/了/着/是） | 半截句特征 |
| **Z06** | 有角色却缺「N岁」或量词（个/位/名/群） | 英文式 `28-year-old` 不认；量词缺失是翻译腔 |
| **Z07** | 主语起手：默认散文方言要求**首句**出现角色名词；medium-first（Krea 2）/tag 分块（SDXL）方言放宽为「角色名词出现在前 60%」 | 中文主语先于谓语；方言顺序不同，判据跟着方言走 |

**规则不能空转**：同一份 IR 的英文输出必须被 Z01/Z03 抓到
（`test_checker_flags_english_output`）；中文输出必须全过
（`test_zh_outputs_pass_machine_rules`）。

## 6. 事实对账口径：为什么中文也能 `lost = 0`

现有 `roundtrip.diff()` 的固定项命中器是**英文词表**（`expand.COLORS` 颜色、
`expand.DIRECTIONS` 方位）。把中文 prompt 直接丢进去，「黄色」会被判成「丢失
yellow」——那是判据的语言问题，不是编译丢了事实。

`zh.fact_surface(text)` 把中文里的**颜色面/方位面归一化回英文规范词**，再把结果交给
既有 `roundtrip.diff()`：

```
IR ──英文渲染──▶ EN prompt ──roundtrip.diff──────────▶ lost = []
IR ──中文渲染──▶ ZH prompt ──fact_surface──▶ 规范词面 ──roundtrip.diff──▶ lost = []
```

- `fact_surface` 只**换面**，不添加事实（反证单测：
  `test_fact_surface_does_not_launder_lost_facts`——删掉「白色」/方位后必须报丢失）；
- 「相等」不只看 `lost`：两边 `extra`（多出来的事实）排序后也必须完全相同；
- 局限：`_COLOR_BACK` / `_DIRECTION_BACK` 是固定词表。词表外的意译会让 `lost` 误报
  （宁可误报，也不静默放行）；扩词表是后续维护项。

`lint.check()` 的中文输出与英文输出**判据一致**（`test_lint_parity_en_vs_zh`）：
L006 年龄闸、L010 图内文字逐字、L001 预算这些与语言无关的项两边同结论；
L017 的英文 `age pattern`、L002/L013 的英文质量词在中文路径自然不触发（不是放过）。

## 9. 判据边界与已知限制

### 9.1 已验证 / 未验证（分开写，别混）

| 断言 | 状态 |
|---|---|
| 英文默认输出逐字节不变 | **已验证**（freeze sha256 对账 + 365 条旧单测） |
| 中英两份事实集合相等（`lost=0`，4 fixtures） | **已验证**（机器判据；`fact_surface` 换面后比对） |
| 中文输出无英文语序的**表面特征** | **已验证**（Z01–Z07 机检；英文输出会被抓） |
| 中文输出母语审校通过 | **未验证**——机器判据证明不了「读起来自然」；§8 人读抽检待 Lead 签收 |
| 中文 prompt 在真实图像模型上效果更好 | **未验证**——本轮没有任何盲评/出图对照（与 G7 同理，不能拿「能翻」当「更好」） |
| `notes` 观察散文的翻译质量 | **机翻**（逐句查表 + 词表兜底），属「机翻痕迹」，不是「英文语序」；未校 |
| `reverse` 命令的 `--lang` | **未接**（本轮只接 compile/lint；reverse 走自己的出词链路） |
| `--mode llm` 的中文扩写 | **未实现**（明确拒绝，不静默降级） |

### 9.2 已知限制

1. **词表边界**：结构化字段的整串值覆盖了仓库 fixtures + examples；词表外的输入走词级
   兜底，英文词会原样保留并在 warnings/Z02 里点名——不会静默吞事实，但读起来会中英混排。
   模型式翻译（LLM 在环）不在本层目标里：本层要求零模型、可复现。
2. **方向词的反向归一化**（`fact_surface`）是固定别名表；新写法（如「左侧偏下」）要先补表，
   否则 roundtrip 会误报丢失。误报方向是安全的（红让人去补表，不放过）。
3. **Layout JSON / bbox 表 / 编辑指令 / H3 时间线**不做整句重排（§3.1），
   它们的中文能力是缺的，不是「已支持」。
4. **`zh_issues` 是表面特征判据**：它能抓 `of the` 式残留、英文标点链、乱序主语；
   抓不到「中文词按英文语序排列但表面合法」的深层乱序（那需要句法分析）。fixtures 的
   自由散文用整句表规避了这个问题；词表外输入没有这个保证。
5. **长度带**：中文 token 口径按「1 汉字 ≈ 1 token」估算（`HeuristicCounter`），
   与各后端真实 tokenizer 有偏差（官方 tokenizer 未接）。预算装箱用它，误差方向是偏保守。
