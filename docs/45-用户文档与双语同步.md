## 2. 同步闸设计（`tools/check_docs_sync.py`，发布闸 S19）

### 2.1 判什么

| # | 判据 | 能抓住的事故 |
|---|---|---|
| 1 | 两份 README 的**标题数量**一致 | 英文加了一节、中文忘了加 |
| 2 | 逐节**层级**一致（`##` 对 `###` 判红） | 中文把子节写成同级，目录结构悄悄变平 |
| 3 | 逐节**编号**一致（`1.2` 对 `1.3` 判红；一侧有号一侧无号也判红） | 两节顺序反了、编号跳号 |
| 4 | H1 各恰好 1 个 | 粘贴时多带/少带一级标题 |
| 5 | 例外清单的每一条**必须写理由**，且不能是「过期例外」（两边都找不到对应标题） | 防止例外清单变成绕过闸的后门 |

### 2.2 不判什么（明确留给人）

- **标题文字是否互译正确**、正文是否等价 —— 中英标题天然不同字（`1.2 Install` / `1.2 装`），
  机器对译不可靠，硬判会变成一堆假红；
- **不带编号的节之间换序**（如「四层读者」与「术语」互换）—— 只判层级与编号，无编号节互换检测不到；
- **表格行级同步**（中英报错表：可见各 14 行、机检计入 13 行）—— 由 S18 对中文表逐字核源码，英文表靠人审；
- 代码块里的 `#` 不参与解析（示例里的注释不是标题）。

### 2.3 例外机制

`tools/check_docs_sync.py` 的 `EXCEPTIONS` 是唯一允许「单侧存在」的地方，格式：

```python
EXCEPTIONS = [
    {"en": "Appendix", "zh": "", "why": "英文附录只在 EN 维护，中文版引用全文"},
]
```

- 每条必须有非空 `why`，否则闸红；
- 匹配到不存在的标题 = 过期例外，闸红（防止「先写例外再删节」的静默漂移）；
- **当前例外为 0 条**：两份 README 完全成对（32 节 / 32 节）。

### 6.1 发布闸全绿的证明方式（共享工作树里有别人未提交文件）

任务要求不 `git add`，而 S16 会因「工作树有未跟踪文件」判红（本轮与其它队友的新文件都在工作树里）。
为了证明**本轮改动本身**能让发布闸全绿，用一个只应用本轮改动的临时 clone 复跑：

```text
$ git clone --shared . <tmp>            # 从 HEAD 起
$ copy README.md README_ZH.md tools/check_release_ready.py \
       tools/check_docs_sync.py tests/test_docs_sync.py \
       docs/45-用户文档与双语同步.md \
       examples/llm-compile-zero-model.json <tmp>/   # M2 的新示例（引用依赖，未提交）
$ git -C <tmp> add -A
$ python <tmp>/tools/check_release_ready.py
S16 黑名单随仓库走 …
S18 文档清单与仓库实物一致
  [OK] 报错表原文能在源码里逐字找到（13 行）
  [OK] 相对链接都指向真实文件
  [OK] 反引号里的路径都真实存在（不是本机留档）
S19 README 中英节级同步
  [OK] 中英 README 节级成对（EN 32 节 / ZH 32 节）  例外 0 条
结果：通过 53 / 失败 0          ← 干净 clone 无本地 token 文件，一项条件检查 [--] 跳过
[exit 0]
```

共享工作树的同一命令会把 S16 判红（未跟踪文件清单里是**所有**未提交文件，不区分归属）；
这属于提交前状态，不是本轮文档改动回归。
