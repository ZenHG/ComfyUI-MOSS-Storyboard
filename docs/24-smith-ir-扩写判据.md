# 扩写：目标、判据、以及为什么「写长点」是错的

> 2026-10-31。这份文档补的是此前最大的一个漏洞：**扩写只有一个模糊的「让模型写详细点」，
> 没有目标定义、没有判据、没有失败模式的分类**。
> 结论先写在最前面，证据和推理在后面。

---

## 0. 三句话

1. **扩写不是增加字数，是降低欠定槽位的熵。** 加词不加约束，等于没扩写。
2. **扩写有两种失败，方向相反**：欠约束（太泛，出十张十个样）与过约束（把用户没说的也写死）。
   只优化其中一边，必然滑向另一边。
3. **扩写必须能判死。** 判死的标准不是「读起来好不好」，是「有没有动用户定下的东西」——
   这一条完全客观、可自动化，且不需要图像生成器。

---

## 1. 先分清三件事：我们把它们混成了一件

| 语义 | 输入 → 输出 | 需要的资产 | 可验证性 |
|---|---|---|---|
| **补全** completion | 「一个女孩站在窗前」→ 加上时间、天气、光、材质 | 默认值库（风格→默认属性） | 中：补的每一项要能追溯到「该风格的公认默认」 |
| **翻译** translation | 中文口语 → 目标方言的术语与结构 | 术语表 + 方言语法 | 高：术语命中率可数 |
| **改写** rewrite | 已详细的长句 → 重排成模型喜欢的顺序 | 句法模板 | 高：事实集合应当不变 |

现在的 `--mode llm` **三件一起做**，所以出问题时无法归因：是补错了、翻错了、还是改丢了？

专家的做法是**拆开、各自可验**：补全查「默认值来源」，翻译查「术语表命中」，
改写查「事实集合不变」（往返校验）。拆开之后每一步都能单独判死。

---

## 2. 目标定义：熵，不是长度

设用户的意图是 I，模型输出图像的分布是 P(·|prompt)。扩写要做的，是让 P 的支撑集
收缩到「用户会认可」的那一小块。

- 「masterpiece, 8k, best quality」对 P 的约束 ≈ 0：它在训练数据里与几乎所有图共现，
  不排除任何东西。写一百个也不缩小支撑集。
- 「雨后的湿沥青把招牌倒映成竖条」约束很强：它同时定下了地面材质、湿度、光源位置、
  反射几何。

所以**判据不是词数，是「每加一句，排除了多少种可能」**。词数只是这个量的一个粗糙代理，
而不同模型的 encoder 对词数的容忍度完全不同（见 §3），所以词数只能当**方言参数**用。

### 两种失败模式

| | 欠约束 | 过约束 |
|---|---|---|
| 症状 | 同 prompt 出十张十个样；主体对了但场景全变 | 画面僵化；模型没有发挥空间；换个 seed 也一样 |
| 根因 | 槽位没填：主体/动作/空间/镜头/光 有空缺 | 把 OPEN 槽位也当 FIXED 写了，或写了互相矛盾的多个方案 |
| 判据 | 词数低于该目标长度带下界 | 出现 IR 里没有的数字/引号文本；同一维度出现多个互斥值 |
| 修法 | 补槽位 | 删到每个维度只剩一个决定 |

**这两种失败必须分开判**。只盯「写长点」→ 过约束；只盯「别乱写」→ 停在欠约束。
绝大多数 prompt 工具只做了前者（各种「增强器」），所以我们看到大量 300 词、
信息量为零的 prompt。

## 3. 业界怎么做：扩写是**模型问题**和**搜索问题**，不是提示词技巧

这一节是我此前缺的部分。按证据强度排：

| 做法 | 事实 | 对我们的含义 |
|---|---|---|
| **DALL·E 3 的 recaptioner** | 训练数据里的 caption 太短，所以 OpenAI **训练了一个模型**把 caption 改写得更详细，再喂给生成模型 | 扩写的第一性问题在**数据分布**，不在 prompt 模板 |
| **FLUX 3 官方 prompt upsampler** | 官方提供专用模型 `flux-3-image-klein-pup`（9B，约 18.8 GB），CLI **默认加载**，`--no-pup` 才关 | 厂商自己承认「短 prompt + 专用扩写器」优于「人写长 prompt」。**我们不该跟它抢这活**，而应把长度压到它喜欢的区间 |
| **Krea 2 的 512 硬截断** | encoder 在 512 token 处**按位置**砍，砍掉的是尾部 | 长不等于好：**顺序**决定什么被保留。重要度排序必须在写之前做 |
| **Promptist / PromptEnhancer** | 用强化学习 / 奖励模型训练一个「prompt 改写器」，目标函数是下游图像质量 | 扩写可以是一个**可优化的函数**，不是一个固定模板 |
| **DSPy / OPRO / TextGrad** | 把 prompt 当可优化参数：采样候选 → 用指标打分 → 保留胜者 → 迭代 | 扩写应该是**搜索**，不是一次生成 |

一句话：**业界没有人靠「写一段更好的系统提示词」解决扩写**。他们要么训练一个模型，
要么把 prompt 当参数去搜。我们现在的做法（一次生成 + 规则约束）只覆盖了「不犯错」，
没有覆盖「更好」——这是明确的短板，已写进 §7。

### 一个反向证据：FLUX.1 与 FLUX 3 的官方说法互相矛盾

- FLUX.1 时代：官方提示「短 prompt 效果更好」（T5 编码器对长文本处理不佳）。
- FLUX 3：官方内置 upsampler，把短 prompt 自动扩成长描述。

同一家、两代产品、相反的建议。**这说明「该多长」没有普适答案，必须 per-model 标定**——
这正是我们把它放进 registry 而不是代码里的理由。

## 4. 为什么「让 LLM 自由扩写」必然失败

和反推踩的是同一个坑：**任务竞争 + 没有账本 + 没有校验**。

1. **任务竞争**：模型同时要做「理解事实」「决定风格」「控制长度」「不违反规则」四件事，
   预算被前三件吃掉，第四件必然失守。反推时我们靠**拆成两遍**解决；扩写这里靠**账本**
   把「不能动的」显式列出来，让它不必自己记。
2. **没有账本**：模型不知道哪些是用户定死的。它会把「28 岁」写成「30 岁上下」，
   因为对散文来说那更自然。**这不是模型坏，是我们没告诉它。**
3. **没有校验**：写完就交，错了也没人知道。所以必须有一个纯 Python 的体检层，
   把「改字」「造数」「造字」这三类硬错误拦下来。

## 5. 我们的架构：账本 → 生成 → 体检 →（一次）回炉

与洗图三段式对称，但**不调第二次模型**（回炉除外，且只一次）：

```
IR ──①账本(纯 Python)──▶ FIXED / OPEN / FACTS / LENGTH ──②生成(LLM)──▶ 草稿
                                                              │
                                        ③体检(纯 Python) ◀────┘
                                        │ 不过 → 带着失败项回炉一次
                                        └ 仍不过 → 报告 fail，不静默
```

### ① 账本（`expand.ledger`）

四段，全部由 IR 推导，不需要用户额外标注：

- **FIXED**：图里的字（逐字）、年龄、用户 `must_keep`、`constraints.fixed`、颜色、方位。
- **OPEN**：clauses 里**没有**的维度——这些才是该扩写的地方。
- **FACTS**：逐条事实，每句必须能回溯到其中一条。
- **LENGTH**：该目标在该档位下的词数带。

### ② 生成（`EXPAND_SYSTEM` + 方言 spec）

系统提示词只留两类内容：**硬规则**（不能动什么、不能造什么）与**方法**
（补槽位而不是加形容词；一帧只定一个构图策略、一个主光、一个媒介）。
方法部分来自交接文档 `新节点-反推与扩写-设计与提示词框架-2026-10-30.md` §5.5 的五点结构
（空间/主体/环境光/色彩材质/文字风格），压缩到能进 token 预算的长度。

### ③ 体检（`expand.verify`）

零模型、零网络、可单测。判据分两级：

| 项 | 级别 | 为什么 |
|---|---|---|
| 图里的字没逐字出现（改标点也算） | **error** | 改了就是另一张图 |
| 年龄 / `must_keep` 丢失 | **error** | 同上 |
| 出现 IR 里没有的数字 | **error** | 最高置信的幻觉信号（可数、可验证） |
| 出现 IR 里没有的引号文本 | **error** | 图里没有这段字 |
| 方位/颜色没对上 | warn | 表达方式本来就自由，方向别丢即可 |
| 词数在长度带外 | warn | 欠约束或过约束，但不算错 |
| 质量词 / 否定式 / 比例进散文 | warn | 污染，不是错误 |

**故意不给总分。** 一个 0–100 分会被当成结论，而这些项量纲不同、代价不同。

### ④ 回炉（最多一次）

把失败项原样回喂：「YOUR LAST ANSWER FAILED THESE CHECKS. Fix only these」。
两遍都错时保留**错得少**的那份，并照实报 fail——不重跑第三遍，因为第二遍还错，
说明是事实层（IR）的问题，不是采样运气。

## 6. 判据的边界：能判「对不对」，判不了「美不美」

必须说清楚，否则会被误用：

- **能判**：有没有动用户定下的东西、有没有编造、长度是否合方言、有没有污染词。
- **不能判**：光的方向对不对、构图好不好、颜色搭不搭、读起来优不优雅。
- **所以**：`verify` 的 pass 不等于「这张图会好看」，只等于「这段 prompt 没有背叛 IR」。
  后者是前者的必要条件，不是充分条件。要判「好看」，只能重生成 + VQAScore + 人。

另外三个已知漏洞（已写进 README §10）：

1. 用户在正文里随口说的「红色」如果没进 IR，就保护不到——**想固定什么，写进 `must_keep`**。
2. `brief` / `detailed` 的长度带是推导值，不是官方值。
3. 一次只出一个候选，没有「采样 N 个 → 用指标选」。

## 7. 还没做的三件事（按性价比）

1. **把扩写改成搜索**（半天）：采样 N=4 个候选，用 `verify` 的硬项 + 长度带距离排序，
   取第一。成本是 4 倍生成时间，收益是方差大幅下降——扩写的主要缺陷本来就是方差。
2. **往返校验**（依赖「prompt → IR」，2 天）：扩写后的 prompt 反推回 IR'，
   与 IR 比对事实集合。丢的 = 欠表达，多的 = 幻觉。**不需要生成器**，这是最便宜的一层验证。
3. **生成侧验证**（依赖 ComfyUI API + VQAScore）：真正回答「重生成像不像」。
   前面两条都只能保证「没背叛」，这条才能回答「有没有用」。

---

## 8. 一句话收尾

> 扩写的好坏，不在于写了多少词，而在于**每一句都排除了什么可能，且没有排除用户想要的那一种**。
