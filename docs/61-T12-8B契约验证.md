### 2.1 关键发现：prompt 契约也必须一起切

27B 时代 `adapters/h3.py` 逐字照抄的是 **27B 仓库**的 `prompt_template.py`：system 一段 +
user 三行 `resolution/duration/original_prompt`。8B 官方仓库的契约不同：

- system 是**另一段更长的官方说明**（5185 字符；含 I2AV/FL2AV 的对齐首行、`[Shot 2] At 00:03.500`
  的时间戳格式要求等）；
- user 是**四行**：`task: t2av` / `resolution: …` / `duration: 8s` / `original_prompt: …`。

LoRA 是在这份格式上训的；喂 27B 模板属于**分布外输入**。本次已改 `adapters/h3.py`：

- 新增逐字照抄的 8B `SYSTEM_PROMPT`；旧 27B 常量保留为 `SYSTEM_PROMPT_27B_LEGACY`（历史参考）；
- 新增 `format_request()`（四行，`task` 第一行）与 `build_messages(..., task="t2av")`；
- `_rewrite()` 用官方 system + `format_request()`；**不再拼接**旧 `LOCAL_ADDENDUM`（保留常量
  `LOCAL_ADDENDUM_27B_LEGACY`）——要贴训练分布，就不能再加本地增补。
- 六段式 profile 的 prompt 不受影响（它本来自成一套）。

### 2.2 doctor 的基座查找修复

8B 基座的 HF 模型 id 是 `Qwen/Qwen3-VL-8B-Instruct`，而官方 GGUF 文件名是
`Qwen3VL-8B-Instruct-Q4_K_M.gguf`（少了两个连字符）。原 `doctor` 按「模型 id 子串」找文件，
找不到正确基座，反而把它列成「同架构的其他基座…不要用」（假红）。
已在 `moss_llm/smith/cli.py` 增加**归一化回退**：去掉所有非字母数字后再比一次子串；
`_name_matches` 的版本号判据不变（3 / 8b 都在文件名里 → 判定「与适配器同款」）。
这是通用修复：任何「HF id 与 GGUF 文件名标点不同」的官方模型都能被正确识别。

作者 README（C 级）称挂 adapter 约 −35% tok/s；本机实测 −25.3%（59.7 vs 79.9），方向一致

### 5.1 H3-PARAM 假阳性（T12 真机暴露，已修）

- **现象**：挂 LoRA 的输出正文里有 "rhythmic steps"（脚步）与 "each stride" 这类自然动作词，
  旧判据 `\bsteps?\b` 把它当结构化参数 steps，`h3 check` 报 `H3-PARAM`——这是那次 fail 的
  **唯一原因**；不挂 LoRA 的输出没有这个词，机检 pass。
- **修法**（`moss_llm/smith/h3.py` 的 `PARAM_WORDS` + `_blank_ts()`）：
  - `steps?` 只认「参数名紧跟数值」：`steps 20` / `steps=20` / `steps: 20`；`rhythmic steps` /
    `footsteps` / `two steps` 不报。
  - 画幅/帧率恢复为**通用规则**并保留白名单漏项：通用比例 `\b\d{1,3}:\d{1,3}\b`（覆盖
    `4:5` / `16:10` / `5:4` / `画幅 4:5`）、显式小数比例 `2.35:1` / `1.85:1`、后置 `fps 24` /
    `fps: 24`；`24fps` / `192 帧` / `resolution 1920x1080` 照旧报。
  - `_blank_ts()` 扩成挖 `At MM:SS[.mmm]`（含省略毫秒的旧写法）——`At 00:03` 是切点时间，
    不是 `00:03` 画幅，挖掉之后通用比例规则才不会误伤。
- **测试**：`tests/test_h3_six.py::TestH3ParamFalsePositives` **9 条**（早前 5 条 + 本任务
  4 条：通用比例、中文后缀、`fps N` 前置、恢复比例后 steps 仍安全）；`test_h3_six` 从 56 →
  **65 全绿**。
- **回归**：`out/h3/8b/with_lora/rewritten.h3.txt` 与 `without_lora/...` 过 `h3 check` 现在都是
  **pass（0 error / 0 warn）**。
- **边界/未验证**：仍是正则启发式——中文「二十步」、英文数字词（"steps twenty"）、
  `step_count` 等变体仍可能漏/误；`At 12:30` 这类「非时间戳语境」的文本会被当作画幅（无法只靠
  正则区分，需上下文）。本次只覆盖 T12 + 复核点名的比例/`fps`/时间戳三类。

## 6. 许可与发行风险

- **LoRA 仓库未声明 license**：HF README/metadata 里没有 license 字段（B：查了
  `model_info` 与 README 头）。因此权重**只用于内部验证**：不提交、不随包发行、不提供下载链接。
- 8B 官方 `SYSTEM_PROMPT` 是逐字取自同一仓库的 `prompt_template.py`；该文本同样没有
  license 声明。本次为契约对齐写入代码，**发布前需确认许可**，或改写成自有的等价说明
  （但那会离开 LoRA 训练分布，效果需重测）。
- 基座 `Qwen/Qwen3-VL-8B-Instruct` 是 apache-2.0（B）；LoRA 的许可空白不因基座许可而消失。

## 7. 未验证 / 不能声称

1. **LoRA 语义是否按训练目标生效**：切点格式判据未复现（§5）；需要官方 infer.py/safetensors 对照
   或 llama.cpp LoRA 支持确认。
2. **质量**：没有人类判读；本机只有一条狐狸句的输出可看，不能给「质量提升」结论。
3. **12 GB 边界**：本次跑前空闲约 9 GiB、ctx 8192 跑通；更小空闲/更大 ctx、以及 `--fit` 实际
   把多少层 offload 到 CPU（本机日志未打印层数）都没有量化。
4. **third-party 转换等价性**：pytraveler 的 GGUF LoRA 与官方 safetensors 是否逐张量等价，
   未验证（不同转换工具可能改变 scale/精度）。
5. **thinking / MTP / 其他任务（I2AV/FL2VA）**：未跑；官方 8B 支持多任务，本次只跑 T2VA 文本路径。
6. **llama.cpp 对 qwen3vl 的 LoRA 支持**：没有查上游 issue/版本矩阵；若上游不支持该架构的
   LoRA 应用，速度差也可能来自其他因素（本次无法把两者完全拆开）。
