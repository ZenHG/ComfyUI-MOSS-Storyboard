# 反推重复循环处置（显式失败 / 合并出声）

> 2026-11-01。对象：`moss_llm/smith/reverse.py::coerce_ir` 的「实体重复循环」处置（M1a-4 / task-38）。
> 背景证据来自 G7 第二轮实测；本文件只记录本任务（reverse 路径 + 测试 + 文档），节点 `caption` 路径未改（见 §6）。
> 证据分级：**A**=本机实跑 ｜ **B**=数据复核 ｜ **D**=工程判断。

---

## 0. 一句话

G7 第二轮发现：模型会把同一批 label 反复写到 **40 条**，`json_schema` 的 `maxItems=40` 在**语法层**
把循环截停成「恰好 40 条合法 JSON」——`coerce_ir` 看到 `dropped=[]`、只有 `capped` 提示，于是
**「跑崩」被当成「成功」**，重复实体还进入 binding 分母污染 A 臂覆盖率。本任务把这种循环从
**静默截断**改成**显式失败**（`ReverseError`，附 Report），轻度重复则**合并 + warning**；
同时保留「恰好 40 个唯一实体」的合法路径。

---

## 1. 问题（G7 第二轮的机制）

```
模型重复写同一批 label（例如 8 种 label × 5 次）
  → json_schema maxItems=40 在语法层截断（JSON 正常闭合）
  → coerce_ir 收到 40 条，dropped=[]，只有 capped 告警
  → 40 条重复实体进入 IR → binding 分母翻倍 / 全表覆盖率被稀释
  → 用户/流程以为「取证成功」，实际是「重复循环导致的静默截断」
```

**实测规模（G7 第二轮，A-4B）**：20 图里 **3 张**、60 图里 **10 张** 命中 `maxItems=40` 的
语法层截断；这些记录 `ok=true`、`finish_reason=stop`，不是「跑崩」，但也不是有效取证。
（B-9B 的 60 图轮另有 **2 张**：img51/img58，见 `docs/G7-反推质量-第二轮.md` §8.2。）
证据指针（相对路径）：`out/g7/round2/json/A-4B/`（20 图轮）、`out/g7/round2/json60/A-4B/`
（60 图轮，跑批产物）；工具侧可配合 `out/g7/round2/compare-20.md` / `compare-20.json` 复盘。

**为什么 `capped` 告警不够**：`capped` 只是「达到上限，请人工确认」，但重复实体已经进了 IR；
下游（binding、编译、G7 统计）仍会把它当数据。所以必须在上限处理**之前**判「重复度」，
把「循环」与「合法 40 条」分开。

## 2. 判据与阈值（实现）

### 2.1 归一化与分组

- `label` 归一化：`str(label).strip().casefold()`；`kind` 同样 `strip().casefold()`。
- 按 **`(kind, label)`** 分组；`"Cup"` / `"cup "` / `"CUP"` 视为同一 label。
- **空 label 不参与重复度**：无法可靠归并的空 label 实体按各自独立处理（不让「一批无 label
  的实体」误判成循环）。这是本任务的**显式口径**（deviation，见 §7）。
- `重复多出的条数 = 有 label 的实体数 − 不同 (kind,label) 组数`。

### 2.2 阈值与两种处置（在「达到上限」处理之前执行）

记 `N = len(raw_entities)`，`EXCESS = 重复多出的条数`：

| 条件 | 处置 |
|---|---|
| `N >= MAX_ENTITIES` 且 `EXCESS >= MAX_ENTITIES // 2`（即重复占比 **≥50%**） | **抛 `ReverseError`**，不返回 IR；错误消息含「疑似重复循环 + N 里有 M 个不同 label + 已按失败处理、避免把语法层截断当成成功 + 建议重试/提高 max_tokens/换模型」；`exc.report` 附本次 `Report`（含 `capped=True / capped_at=N / warnings`） |
| 其它有重复（未达上限，或达上限但占比 <50%） | **只保留同 `(kind,label)` 的第一条**，其余合并；`report.warnings` 写「合并 k 条重复实体（(kind,label) 归一化后相同，只保留第一条）：label 列表」，不静默 |
| 无重复 | 原逻辑不变 |

随后才执行原有「达到上限」逻辑：

| 场景 | 结果 |
|---|---|
| 39 个唯一实体 | 成功；不触发 `capped`（不误报） |
| **40 个唯一实体** | 成功；`capped=True / capped_at=40` +「疑似截断，请人工确认」 |
| **41 个唯一实体** | 截断到 40；`capped=True / capped_at=41` + `dropped` 含「超过上限」 |
| >40 唯一实体 | 截断 + `dropped`；`capped_at` 记合并/截断前的原始条数 |
| 40 条、仅 1 条重复（2.5%） | 不失败；合并到 39 条 + warning；仍按原始 40 记 `capped` |
| 40 条、8 个 label 循环（重复占比 80%） | **`ReverseError`**（哪怕 JSON 闭合、`ok=true`） |

### 2.3 为什么是 50% / `MAX_ENTITIES // 2`

**这是工程判断，不是统计结论（D）**：

- 真实「恰好 40 个合法实体」的画面极少；若只是少量重复（例如 40 条里 1–2 条重复），
  合并后损失很小，不该把整个单元判失败——所以需要一个「明显不正常」的门槛；
- 观测到的循环形态是**极端**的（8 个 label × 5 次、1 个 label × 49 次），重复占比远高于 50%；
- 取 50%（`MAX_ENTITIES//2`=20）是「宁可让明显循环失败、不误杀少量重复」的折中；
  **没有真机频率数据**来校准这个阈值，下一轮可以按实际分布再调（见 §6 未验证）。
- 若有人担心误杀：错误对象附 `Report`，且错误消息给出了重试/提高 max_tokens/换模型的建议；
  错杀成本是「重跑一次」，漏放成本是「污染一张图的 binding 全表」。

## 3. SYSTEM 规则 17 强化

原规则只写「List each entity exactly once / Never repeat the same label with different anchors /
entities must not exceed 40」，模型在降级档仍会重复凑数。现改为（`reverse.py` 规则 17）：

> Every entity label must be unique. Merge multiple instances of the same thing into ONE entity
> whose label carries the count ("two ceramic cups", not two cup entries). If you notice you are
> repeating the same label or fact, STOP repeating and output the JSON immediately — never pad
> the list to look thorough. entities must not exceed 40 items.

代码里在 `SYSTEM` 常量上方加了中文注释，说明「改哪条（17）、为什么（旧规则挡不住降级档的
重复凑数；语法层 maxItems 会把循环截成合法 JSON）」。

## 4. 行为矩阵（一句话版）

- **唯一实体**：39 不告警 / 40 capped 告警 / 41 截断 + dropped —— 保留 M1a-3 语义。
- **重复循环**：达到上限且重复多出 ≥20 条 → **显式失败**（`ReverseError` + Report）。
- **轻度重复**：合并第一条 + warning（条数 + label 列表），不失败。
- **未知 kind**：仍走原有字段闸（M1a-2/M1a-3 行为不变）。
- **空 label**：不参与重复度统计，原样保留（§2.1 口径）。

## 6. 两路径边界与未验证项（诚实清单）

### 6.1 节点路径（本轮**未改**）

- 节点 `MossPromptSmith` 的 caption 路径走 `nodes.py::guard_caption_json`（inventory subjects/props），
  与本文件的 `coerce_ir` 是两套数据结构；**本轮不改 nodes.py**。
- 节点 caption 通道**尚未观测到同类重复循环**（没有真机跑批数据）；它的数组上限只是
  「达到上限出声（capped 文案）」，**没有本文件的「≥50% 重复即失败」硬闸**。
- 因此：节点路径的重复循环处置列为**未验证边界**；若后续在节点真机跑批里看到同类循环，
  需要把本判据移植到 `guard_caption_json`（另开任务）。

### 6.2 未验证 / 不能声称

1. **真实服务端语法层截断仍无端点复现**：本任务验证的是「`coerce_ir` 收到 40 条重复时」的处置；
   「服务端 grammar 先在 40 条截断」仍是 G7 侧观测 + 代码推断，没有可复现的 json_schema 端点。
2. **50% / `MAX_ENTITIES//2` 是工程判断**，不是统计结论；真实「恰好 40 个合法实体」的分布与
   误杀率没有真机数据。
3. **效果幅度未测**：本任务不跑 GPU；「A 臂 binding 分母污染因此减少多少」需要下一轮 G7 测量。
4. **节点路径未覆盖**（§6.1）；**空 label 口径**是显式选择（§2.1），不是唯一正确解。
5. 重复合并只保留第一条的**描述字段**（不合并 descriptors）；本任务目标是「别把循环当成功」，
   合并后的实体质量不在本轮评估范围。
6. **`coerce_ir` 与 `decompose` 共用**：`moss_llm/smith/decompose.py` 也调用同一函数，重复循环
   处置同样生效；错误会由上层包成 `DecomposeError("抽取为空：…")`——未被吞掉，但前缀会误导，
   排查时按 `__cause__`/消息里的「疑似重复循环」定位。另：`_norm_kind` 未走 `_KIND_MAP` 的
   别名归并（如 `"person"` 与 `"character"` 不会视为同一 kind）、合并只保留首条的 descriptors，
   真实循环里未观测到由此漏判，列为残余风险。
