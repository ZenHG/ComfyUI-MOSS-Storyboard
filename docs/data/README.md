这里放**公开可复核**的原始读数。README 与 `docs/` 里凡是给出来的数字，都应该能在本目录找到对应文件。
**不随安装包分发**（`docs/` 被 `.comfyignore` 排除），只对 GitHub 读者可见。

| 文件 | 回答什么问题 | 引用它的地方 |
|---|---|---|
| `g1-results.json` | 12 GB 卡在各档「格数 × 单格长边」下的显存峰值 | `README.md` / `README_ZH.md` 显存段 |
| `g1-report.md` | 上表每一跑的原始记录与口径（含哪些数字不可用） | 同上 |
| `g2-50-3.json` | 50 步 / cfg 3.0 档下「整张 vs 逐格」的一致性读数 | `README.md` / `README_ZH.md` 的 `mode` 段、`docs/07` |
| `recipe-fix.json` | 单字段实验：全局段多一句「同一对人物」是否影响结果 | `docs/15-recipe-contract.md` §六 |

## 口径与边界（读之前先看）

- **没有耗时数据。** 本包不是加速节点，`README` 不出秒数、不出倍数；这里也没有。
  历史留档里出现过的秒数一律不可横向比较（换了机器、换了宿主版本、换了配方）。
- **`g1` 与 `g2` 不同源。** `g1` 是「带 4 步蒸馏 LoRA 跑 50 步」的显存组，只用于看峰值趋势与余量；
  `g2` 是无 LoRA 的 50 步一致性组。两者不能混着比。
- **`g1` 的 `delta_mb`（相对基线的增量）不可用**：基线本身在 9006–10423 MB 之间抖（跨 1.38 GB），
  而六组峰值只差 183 MB。任何「这一档比那一档多占多少」的说法都超出这套数据的分辨率。
- **峰值含桌面噪声**（约 ±200 MB），且是单次跑值，不是多次取中位。
- **`g2` 是单场景、单 seed 的成对样本**，不是分布。`docs/07` §五另有一组 ArcFace 校准（52 对正样本里
  18 对检不到脸，占 35%）⇒ 身份指标**只报数，不许当放行判据、不设阈值**。
- 逐格/整张的拼图（`g2-50-3/*.png`）**没有随仓分发**：单张就几 MB，而且判读要靠原尺寸目检，
  缩略图会误导。需要复核可以按 `g2-50-3.json` 里的种子与夹具自己重跑。

## 怎么复跑

1. 按 `docs/15-recipe-contract.md` 的配方契约准备稿子（段数 = 格数、全局段声明宫格）。
2. 用 `examples/` 里对应的工作流，按 JSON 里记录的 seed / steps / cfg / LoRA 状态跑。
3. 对照本目录的读数看趋势；**不要逐个小数位比**——同机重跑会抖。

## 为什么这些文件在这里

原先它们只存在于维护者的内部实验记录里，而 `README` 直接引了那个路径 —— 对仓库外的人来说是死链。
现在把读数搬进 `docs/data/`，`tools/check_release_ready.py` 的 S11 会拦住「公开文档又去引内部目录」。
