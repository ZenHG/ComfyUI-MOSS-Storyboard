## 2. 代码路径（D）

- **smith 路径**：`coerce_ir` 在 `raw_entities` 归一成 list 之后、建实体循环之前：
  `len(raw_entities) >= MAX_ENTITIES` → `r.capped=True`、`r.capped_at=len(raw_entities)`、
  `r.warn("实体数达到上限 40：疑似截断，请人工确认（…）")`；`len > 40` 时再记一条
  `dropped`（含「超过上限」与「已丢弃多出的 N 个」）并把 list 截到 40。
  告警文案不含断言词，只有「疑似截断，请人工确认」，并注明「少于 40 个的合法画面不会触发」。
- **节点路径**：`guard_caption_json._cap(container, key, limit, name)`：
  `len(arr) >= limit` 时写 `反推实体上限（capped）：…（达到上限 N；疑似重复/截断，请人工确认）`；
  `len(arr) > limit` 时仍截断并报「丢 N」。覆盖 `subjects 12 / props 32 / materials 16 /
  text 24 / visible_text 24 / must_keep 8 / uncertainties 8`。
- **单遍/两遍同一处**：全仓 `guard_caption_json(` 调用点只有 2 处——
  `nodes.py:445`（单遍，`_run_once` 之后）与 `nodes.py:512`（两遍，pass1 之后 pass2 之前）；
  两条路径的 notes 都通过 `report.extend` 进入同一个 report。
- **向后兼容**：`Report.to_dict()` 在 HEAD 版本的 7 个键
  （`image/size/warnings/dropped/entity_count/age_gate/raw_chars`）之外，追加
  `kind_downgrades/age_dropped`（M1a）与 `capped/capped_at`（M1a-3）；没有改名或删除旧键。

## 4. 发现（只记录，未改文件）

### F1（低，测试缺口）>40 场景的 `capped` 没被作者测试断言

`test_runaway_entity_list_is_capped_and_reported`（49 个）只断言了「截到 40 + `dropped` 含超过上限」；
`test_entity_count_at_limit_is_flagged_as_possible_truncation`（40 个）才断言 `rep.capped/capped_at`。
「**超过**上限时 `capped` 也必须为 True」目前只由本复核探针覆盖（实测 41 → True/41）。
**建议**：给 49 用例补 `assertTrue(rep.capped)` 与 `capped_at == 49`，防止未来只改 `>=` 分支
或只改 `>` 分支时丢掉其中一条告警。

### F2（低，文档口径）`docs/42` §2.5 未标「已验证/未验证」

§2.5 写「已修」并给了机制与测试口径，但全文没有「已验证（本机单测）」这一类证据标签
（docs/46 有 §5 未验证清单、也有「已验证」字样）。任务口径要求「结论区分已验证/未验证」。
**建议**：在 §2.5 末尾加一行「已验证：本机 24/21 条单测 + 构造 39/40/41 探针；
未验证：真实服务端的语法层截断行为（无可用端点）」。

### F3（观察，低）`capped_at` 在 >40 时是「原始条数」而不是上限

41 个实体时 `capped_at=41`（docs/42 §2.5 明确写了 `capped_at=len(raw_entities)`，与代码一致）；
但键名容易被读成「被截断在 40」。若消费方想拿上限，应读常量 `MAX_ENTITIES`。
**建议**：在字段注释里再点一句「>上限时这里是原始条数」，或把它改名（改名会破坏 M1a-3 的新键，
不推荐；补注释即可）。

### F4（观察，低）节点路径只有文本标记，没有机器可读字段

节点 `report` 是字符串列表，capped 只体现为 `反推实体上限（capped）：…` 这种文案。
下游若要程序化统计（例如 merge 报告里数「有多少单元触顶」），只能解析文案。
**建议**：本轮不改；若 G7 round2 的统计需要，可在 `_checks` 或 report 组装时另加结构化计数
（属于接口扩展，需单独评审）。

### F5（未验证边界）恰好达到上限的合法画面误报率

`subjects=12`、`props=32` 的合法画面也会出声（设计上就是「疑似，请人工确认」）。
本机没有真机数据，无法给误报率；docs/42 也没有声称这部分已验证。
这不是缺陷，属于**未验证边界**：需要在一次真实 caption 跑批里看「恰好 12 个主体」出现频率。

## 7. 复现方法

```python
# smith：39/40/41 三档
from moss_llm.smith.reverse import Report, coerce_ir, MAX_ENTITIES
def obs(n):
    return {"entities": [{"id": "e%d" % i, "kind": "character", "label": "man",
                          "descr": {"gender": "man"}} for i in range(1, n + 1)]}
for n in (39, 40, 41):
    rep = Report(); ir = coerce_ir(obs(n), rep)
    print(n, rep.capped, rep.capped_at, rep.dropped, len(ir.entities))

# 节点：恰好上限 vs 差一
from moss_llm.nodes import guard_caption_json
def subjects(n):
    return {"subjects": [{"kind": "person", "role": "s%d" % i, "appearance": "x",
                          "pose": "standing"} for i in range(n)]}
for n in (11, 12, 20):
    out, notes = guard_caption_json(subjects(n))
    print(n, len(out["subjects"]), notes)
```
