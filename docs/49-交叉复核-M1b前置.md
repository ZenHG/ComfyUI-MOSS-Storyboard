## 4. 发现的问题（只记录，未改任何文件）

### F1（中）`verify_manifest` 不是只读：验证失败会**重写 manifest**，第二次验证自愈

- **静态证据**：`tools/g7_round2.py` 第 441 行
  `new = collect_manifest(Path(manifest), root=root)   # 先算新集合（会重写同内容清单）`
  → `collect_manifest()` 内部 `dest.write_text(...)`。即 `verify_manifest` 在**验证**时把 manifest
  覆盖成「当前状态」。
- **动态复现（temp 小目录，不碰 out/g7）**：
  1. 拍 manifest（`binding.json` 记下 sha A）；
  2. 篡改 `binding.json`；
  3. 第一次 `verify_manifest`：`ok=False, changed=["binding.json"]` —— **但 manifest 已被重写成新 sha**
     （实测 manifest sha `9696f9e3… → 11a02c7b…`）；
  4. 第二次 `verify_manifest`：**`ok=True`** —— 失败证据已被覆盖，链自愈。
- **影响**：manifest 是「第一轮产物未被改动」的证据链；一旦有人先跑一次（或某次验证失败后再跑），
  快照就追认篡改后的状态，无法再证明「改动前是什么」。CLI `verify-manifest` 即使全对也会
  **更新 manifest 的 mtime**（内容相同），与「只读证据」的直觉不符。
- **建议修法（由 g7-gold 决定，未改）**：把「收集」与「写盘」拆开——`verify_manifest` 用纯函数
  收集 `{rel: sha}` 后与旧清单比较，**不写文件**；只有 `manifest` 子命令才写。或在写入前
  保留旧文件（write 到临时再原子替换 + 仅在 `manifest` 模式）。
- **本次影响**：我没有对真实 `out/g7/round1-manifest.sha256` 调用 CLI `verify-manifest`
  （否则会改 mtime）；用**副本 + root=真实 out/g7** 验证通过（只读真实产物，仅写 temp 副本）。

### F2（低，但 M1b 会用 60 图）：markdown 的「全部 20 图」标签写死

- `format_markdown()` 第 308 行：`name = "全部 20 图" if key == "__all__" else key`。
- 复现：用 **60 图** 的 images 列表跑 `compare` → 材质覆盖率表的 `__all__` 行仍写「全部 20 图」，
  而 `cmp["images"]=60`。M1b 第二轮正是 60 图，报告表会把分母口径读错。
- 建议：`name = "全部 %d 图" % cmp["images"]`；单测钉住 20/60 两种输入。

### F3（观察，非缺陷）`images60.json` 的 `index` 字段混合类型（53 int + 7 str）

- 7 个补充候选写成 `"s01"…"s07"`，其余是整数。`g7_gold60.py` 已做类型感知排序/格式化
  （第 305–306 行 `0 if isinstance(int) else 1`、`fmt_idx`），`verify` 通过；所以**是设计选择**。
- 注意：外部脚本若直接 `sorted(i["index"])` 会 TypeError（本次复核第一版脚本就撞到，已改为按 id 读）。
  建议在 images60 的 metadata 里加一句「index 混合 int/sNN」或统一成字符串，减少下游踩坑。

### F4（观察，非缺陷）20↔60 口径混用会制造假「失败率变化」

- 失败率分母是「应有张数 = images 条数」；若把 **images60（60 条）** 配 **第一轮 20 条落盘 JSON**
  做对比，r1 会按 40 条缺记录计失败（实测 40/60=66.7%），与代码改动无关。
- 工具本身没错（两轮使用同一 images 列表，分母一致）；这是**用法警告**：M1a 前后同批对比要用
  `images.json`（20 张）；60 图只用于第二轮自身覆盖率/失败率（或与同跑 60 的另一次对比）。
  建议 M1b 报告在失败率表头显式写「同批 20 图」或「第二轮 60 图（无第一轮对照）」。

### F5（观察）calibration 两个产物不在盘上，manifest 只覆盖现存 47 个文件

- `ROUND1_PATTERNS` 期望 9 个非模型产物 + 40 个模型 JSON = 49；实际 manifest 47 行。
- 盘上缺 `out/g7/calib/machine_cells.json`、`out/g7/calib/calibration.json`（`inspect/stats.json` 等在）。
  `docs/G7-反推质量-第一轮.md` §10 曾把它们列为产物。
- 不影响本轮四项算术（都用 `run/batch-summary.json` + `json/**` + `images.json`），但「第一轮完整证据链」
  少了两块；若后续有人拿 calibration 数字复算，需先说明文件缺失。`verify` 只能保护已存在的文件，
  对「从未进快照的文件」无能为力。

## 6. 未覆盖边界

1. **没有真实 round2 数据**（GPU 跑批还没开始）：四项算术是用合成已知答案验证的；真实数据下的

   F1 的动态复现是在 temp 小目录做的，真实 CLI 的「写回」行为由静态代码 + 同一函数路径证明。

5. mtime 比较用 `stat().st_mtime_ns` 精确到纳秒；跨文件系统（若有人移动 out）会失真，本次未发生。
